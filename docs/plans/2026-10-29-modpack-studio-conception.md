# Modpack Studio - design (v2, after the full logic pass)

> Design record. In these plans `BASE` is the base modpack (role `upstream`) and `OWN` is your modpack (role `own`); the real names are settings.
>
> Identifiers in these records were neutralised (`base_*`, `own_*`); the code may still use older names for some persisted values and helpers, so check the source before relying on a name.

Status: v1 written 2026-10-29 from 5 parallel research passes; v2 the same day after the user's clarifications (profile matrix,
two machines, Node/TypeScript) and a double logic review (author + independent Opus reviewer). Nothing is built yet.
**[verified]** = checked in a source by the research; **[to re-check]** = must be confirmed before relying on it.

## 1. Goal

A self-hosted local web app on the user's Minecraft **Studio PC** (test/deploy) that maintains **OWN** (his custom pack built on
BASE) without ever redoing work between two BASE or OWN updates:

- compare BASE server pack, BASE client and OWN: updated / added / missing mods, NeoForge version on every side (must match);
- classify mods client / server / both; keep a server blacklist derived from BASE's own choices;
- compare config profiles, show differences, let him choose (his / BASE's / the server's / edit), remember every choice and replay
  it intelligently on the next version (later also another loader or Minecraft version);
- harvest the settings he changes live on the running server and client, and turn them into reusable customizations;
- build the CurseForge player pack and the server pack, regenerate the first-join message, publish (automated, opt-in);
- deploy to the server PC through the host panel with a world-safe backup and a real rollback;
- embed a Claude assistant with access to the app's data (default Sonnet 5.5, everything adjustable);
- never blind-overwrite a file; every write is previewed, journaled and reversible.

## 2. Machines and runtime (consistent everywhere)

| Machine | Role | Runs |
|---|---|---|
| **Studio PC** (test/deploy, the maintainer starts it 2026-10-29 evening) | clients, BASE zips, this app | Studio as a **logon task under the user's user account** (not a LocalSystem service: SMB needs a user's credentials) |
| **Server PC** (the current PC) | Host panel + OWN server, **receives and runs only** | `deploy-agent` (Node, started at logon with a watchdog) |
| **Another PC** | OWN client really played (`run`) | nothing; read **read-only over a network share** from the Studio |

The host panel API key stays on the server PC: only the agent talks to the host panel, the Studio never sees that key.

## 3. Versions and profiles (the data backbone)

**Pack versions**: `base_version` (e.g. 8.3 with its MC and NeoForge versions) and `own_version` (his numbering, with
`base_pack_ref` and `own_hotfix` counter for hotfixes on the same BASE base). Loader rule: OWN client == OWN server; differing
from BASE only with an explicit override.

**Profile** = a labelled snapshot of a folder set: `pack` (BASE | OWN) + `pack_version` + `side` (client | server) + `state` +
`location` (zip | local path | SMB path | agent snapshot). Every combination is optional; the UI shows the matrix with what exists.

| State | Meaning | Rule |
|---|---|---|
| `clean` | never launched, only creator-forced configs | immutable snapshot; refused if launch artifacts exist (`logs/`, `options.txt`, `*.bak`, `world/`) |
| `launched` | started once (generated files, auto-corrections) | immutable snapshot |
| `run` | really used and tweaked on the fly | read-only capture, refused while the game/server process runs |

Matrix: for each pack version there are client and server in `clean` / `launched` / `run`; **old versions keep only `clean`**
(their jar bytes are not kept either, only metadata). The Studio itself **produces** the `OWN clean` profiles (its builds); old ones
are imported from earlier zips. A server has no `launched` profile unless the agent captures one right after the first boot.

Derivations (each is a plain semantic compare of two profiles):

| Question | Compare |
|---|---|
| What did the BASE authors change? | `BASE new clean` vs `BASE old clean` |
| My own layer on top of BASE (mods + configs) | `OWN old clean` vs `BASE old clean` |
| Noise generated by the game (ignore) | `launched` vs `clean` |
| **What did I tweak live?** (harvest) | `run` vs `launched` (server: vs its post-first-boot baseline) |
| Did the rebuild keep my intent? | `OWN new clean` vs (`BASE new clean` + replayed customizations) |
| Client/server in sync on shared settings? | `client run` vs `server run`, shared (`-common`) config files only |

Live tweaks are compared with `launched`, never `clean` (a first launch already rewrites files).
**Bootstrap**: today's server has no baseline; the first harvest compares with `OWN server clean` and marks every item
"unverified". A value that the first boot auto-corrects right after the Studio deployed it signals an invalid intent, not noise.
Excluded from every compare: `logs/`, `crash-reports/`, `usercache`, `ops/whitelist/banned-*`, caches, saves, secrets.
**Exception**: `<level-name>/serverconfig/**` (level name read from `server.properties`) is included, because NeoForge reads
per-world server configs there and `defaultconfigs` only fills missing files.

## 4. Mod comparison (by mod id, not file name)

Sets: `BASE-S` (server pack, jars), `BASE-C` (BASE client, an untouched instance with jars; Q1), `OWN-C` (Clean OWN client).
**Precondition**: `BASE-C.version == BASE-S.version` and the same NeoForge/MC; else the side derivation is blocked.

- BASE's own choices (ground truth): `BASE-C − BASE-S` client-only, `BASE-S − BASE-C` server-only, intersection both.
  The client-only set seeds the blacklist (one click); it is **recomputed on every import** (`origin = base_derived | user`,
  `valid_for` = BASE version) because BASE can change a mod's side.
- **the user's layer = `OWN-C` vs `BASE-C`** (client vs client): updated / added / pinned. Never compare a client set with a server set.
- **Anomaly** = `BASE-C − OWN-C` (a mod BASE has and OWN lacks; the maintainer does not remove mods). An unresolved anomaly **blocks the build**
  (the server would otherwise get a mod its clients lack and fail the registry check on join). Resolve: restore / accept removal / pin.
- Across BASE versions: a mod BASE removes but OWN still has becomes "OWN-kept" (a decision); a mod updated by both BASE and the maintainer
  is a conflict (his pin or BASE's version).
- **Server pack** = `BASE-S` + (the user's added/updated mods that are server-allowed, section 5); replaced jars go to quarantine.
- **Identity rules**: key = the top-level jar's mod id(s) read from `META-INF/neoforge.mods.toml` (then legacy `mods.toml`,
  `fabric.mod.json`); a jar may declare several ids; jar-in-jar entries are informational, never top-level; library jars without
  a mod id are keyed by `Automatic-Module-Name` + fingerprint; `${file.jarVersion}` is resolved from `MANIFEST.MF`; a duplicate
  top-level id is a build blocker.
- **Versions**: Maven `ComparableVersion` ordering (as NeoForge does). Result: `updated`, `downgraded`, or `different` when the
  strings are not comparable; same id + same version + different hash = `rebuilt`. A `pin` decision silences an intentional
  downgrade. A renamed id (same `cf_project_id`, new mod id) auto-suggests an alias.

## 5. Mod side classification (confidence cascade)

Only mods **new in OWN** need it. Highest priority first; disagreement marks "uncertain" and sends the mod to the boot test.

1. the user's decision (remembered, keyed by mod id).
2. Boot-test proof: `Attempted to load class net/minecraft/client/... for invalid dist DEDICATED_SERVER` = client-only [verified].
3. BASE membership (section 4).
4. `@Mod(dist = Dist.CLIENT)` (one class only; a mod can also have a common entry point).
5. Modrinth `environment` by file hash (bulk `version_files`, no key, 300 req/min, unique User-Agent) [verified]; author-set, not moderated.
6. CurseForge file tags "Client"/"Server" (needs a key; no tag = keep) [verified via Prism / mc-image-helper].
7. Community list (itzg `cf-exclude-include.json`).
8. Bytecode heuristic: weak, last.

NeoForge metadata is weak: `side` exists only on `[[dependencies]]` and defaults to BOTH; `displayTest` / `clientSideOnly` are old
Forge fields [verified]. Checks: unmet or incompatible dependencies (`versionRange`), duplicates, and the **boot test** on the Studio
PC (Java 21, ~8 GB; success = a `Done (...)!` line in a log newer than the start; failure = a new `crash-reports/` file;
one crash is found per boot, so a bisect budget is planned).

## 6. Config engine and customization memory

**Files are classified first**: added/removed upstream, user-only, run-only (generated), renamed. Config files carry a side
(`-client` / `-common` / `-server`): the server build takes only the matching subset of the user's layer.

**Merge inputs (per file)**: `O` = BASE old clean, `A` = BASE new clean, `B` = OWN old clean (O + my layer); output = `OWN new clean`
= `A` + replay of (`B − O`). The live `run` file is **never a merge input**; it feeds harvest (section 7). Classes per setting:
unchanged / only mine / only upstream / same change / **true conflict** / upstream removed a key I changed / moved-renamed /
type changed. Choices per item: mine / BASE / server / edit manually (integrated editor).

**Semantic, not textual.** Files are normalized to settings `{path, key, section, type, value, comment, span}`. Alignment cascade:
exact path -> same leaf elsewhere -> same section/type/similar comment/same old default -> fuzzy name. **Safety rules**:
- only an **exact-path match whose `guard_old` equals the upstream value** applies without a click (still listed in the report);
- a "same leaf elsewhere" candidate is accepted only if unique and at least 0.2 above the runner-up; otherwise it is asked;
- a `guard_old` mismatch is a conflict, never a write;
- a confirmed alias carries a version range and is re-validated by type and guard before reuse;
- `operation.list_semantics = atomic | set | ordered` (default `atomic`; id lists may be `set`; priority lists are `ordered`).

**Memory stores intents, not files**: `customization` (title, rationale, tags, `scope = personal | pack`) -> `target` (file glob, key
path, anchor with aliases / comment fingerprint / type, applicability ranges) -> `operation` (set | remove | append | remove_item |
replace_text | kjs_patch, `guard_old`, `new_value`). Decisions are keyed by (target, value hash) so a rejected item does not return;
`ignore_forever` covers mods that write runtime state into `config/`. Export/import as one YAML per customization; append-only
`event` history; optional git mirror.

**Safety nets for every format**: parse, edit, serialize, then line-diff the result; any change outside the target's span rejects
the library output and falls back to a line-anchored patch. Binary or >2 MB files are opaque (hash, whole-file choice). Keep
BOM/EOL/encoding. Atomic writes (temp + replace, retry on locked files), pre-apply snapshot, undo per run. Secrets are masked in
UI/logs and excluded from AI payloads. Windows traps handled: case-colliding zip entries, long paths, never ordering by mtime across PCs.

**NeoForge facts** [verified]: `defaultconfigs` is copied only when the target file is missing; server configs load from `config/`
with a per-world override in `<level>/serverconfig`; NeoForge rewrites/auto-corrects files and keeps `.bak` copies, so profiles
are compared semantically.

**First-join message**: never edit BASE's `kubejs/server_scripts/announcements/announcements.js`. Generate
`kubejs/server_scripts/own/welcome.js` from a template (OWN version, mods added/removed/updated, this cycle's customizations,
dismissal tracked in player persistent data); MOTD templated in `server.properties` (non-ASCII written as `\uXXXX` escapes
[to re-check]).

## 7. The update workflow (fixed order)

Import -> **Loader check** -> **Harvest** -> Mods -> Sides -> Configs -> Test (boot) -> Build -> Deploy -> **Baseline capture**.

1. *Import* the new BASE zips (server + client) as immutable `clean` snapshots.
2. *Loader check*: NeoForge/MC equal on BASE-S, BASE-C, OWN-C; blocks otherwise.
3. *Harvest* (mandatory before anything that writes): `run` vs `launched` on the server (through the agent's read-only snapshot
   endpoint) and on the other-PC client (SMB read-only) -> proposals (`pending / accepted / rejected / ignored_forever`).
4. *Mods* and *Sides*: sections 4-5. *Configs*: sections 6, merge to `OWN new clean`.
5. *Test*: boot `OWN server clean` headless on the Studio PC; this also yields the `launched` profile of the new version.
6. *Build*: player pack and server pack from **clean** trees only (never from `launched` or `run`).
7. *Deploy*: section 8. 8. *Baseline capture*: the agent snapshots the server right after the first healthy `Done`, before any
   player or tweak, and again after every deploy including hotfixes.

## 8. Builds, deployment, publishing

**Player pack (CurseForge)**: `manifest.json` + `overrides/` + `modlist.html`. Ids come from the OWN client's
`minecraftinstance.json` (`installedAddons[]`), no API key needed [verified from a public sample]; mods added outside the CurseForge
app have no entry there: fallback = overrides if permitted, else manual. Mods not allowed for third-party distribution go in the
manifest only. `.mrpack` export is a later add-on.

**Deploy agent** (server PC): own token **and HMAC** over the payload with a timestamp/nonce and an idempotency key `deploy_id`;
one deploy at a time; allowlisted roots; no arbitrary command. Journaled state machine:
`received -> verified -> stopping -> stopped -> backed_up -> applying -> applied -> starting -> healthy | failed -> rolling_back -> rolled_back`.
- the agent refuses to write a file whose current hash differs from the Studio's `expected_pre_hash` (unharvested live drift);
- stop through the host panel API and **verify** status 0 before touching files; free-space check first (backups + quarantine);
- backup = **files + world together**, taken while the server is stopped, before the first boot of a new mod set;
- health = a `Done` line newer than the start + still alive after N minutes + no new `crash-reports/` file;
- a restart of the agent while `applying` triggers an automatic rollback; rollback = files + world (no host panel backup-restore
  endpoint was found [to re-check]); the last healthy build and its pre-apply snapshot are kept until the next deploy has been
  healthy for X days; quarantine has a retention rule. Notifications go through the notification webhook (Studio needs its own).

**Publish to CurseForge (automated, opt-in)**: the author upload API (separate author token, `.../api/projects/{id}/upload-file` with
a metadata JSON, `parentFileID` for the server pack) [to re-check: no 2026 official page found; modpack moderation applies].
Dry-run, then an explicit click; before uploading it lists existing files to avoid duplicates; token in the Windows Credential
Manager. **Public publishing is blocked** until permission is obtained for BASE-derived content (BASE's repository shows no
derivative licence); unlisted/private is allowed. Same pattern later for Modrinth. Release report: diff between two OWN versions
-> French changelog (also feeds the welcome message).

## 9. Storage and data model

Blobs live **on disk** (sha256-addressed, reference-counted, garbage-collected), not in SQLite. Jar bytes are kept only for the current
OWN and staged builds; every snapshot keeps jar **metadata** (id, version, side, hash). Old versions: `clean` only. Rescans use
size+mtime only as a cache hint and hash before trusting it.

Tables: `pack_version`, `profile(pack, pack_version, side, state, location, source_id, captured_at, manifest_hash, immutable)`,
`file`, `jar(sha256, cf_fingerprint, filename, size)`, `jar_mod(jar, mod_id, version, is_jij, parent_jar, metadata_file)`,
`mod_side(side, origin, confidence)`, `blacklist(origin, valid_for, reason)`, `customization/target/operation`, `alias`,
`proposal`, `decision`, `apply_run` (journaled, same states as deploy), `deploy(deploy_id, build_id, state, baseline_profile,
pre_apply_snapshot)`, `build`, `document` (+ versions), `job`, `setting`, `audit_log`, `chat_*`, `event` (append-only, undo).
Sources: `upstream_server_zip | upstream_client | own_client | own_client_run (SMB) | server_run (agent)`.

## 10. Stack (decided: Node 24 LTS + TypeScript)

| Layer | Choice |
|---|---|
| API | Fastify, REST `/api/v1`, zod schemas shared with the UI, OpenAPI generated |
| DB | SQLite (`better-sqlite3`) + Drizzle migrations |
| Jobs | persisted queue, `piscina` worker pool, per-resource locks, cancel, `interrupted` on restart |
| Live updates | one SSE stream `/api/events` (also chat streaming) |
| Zip | `yauzl` read (jar-in-zip via buffer), `yazl` write |
| UI | React + Vite, TanStack Query/Table/Virtual, shadcn/ui + Tailwind, `cmdk`, `sonner`, French i18n |
| Diff/editor | CodeMirror 6 + `@codemirror/merge` (side-by-side and inline, 3-way from two views) [verified v6.12.1] |
| Configs | `toml-edit-js` (WASM toml_edit), `jsonc-parser`, `smol-toml`, `ftbq-nbt`, `recast` (KubeJS), line-anchored patcher |
| Tests | Vitest + Playwright, synthetic fixtures only |
| Packaging | versioned folder with a pinned portable `node.exe`; `versions/x.y.z` + `current`; DB backup before migration; start by logon task |

Layout: `src/server/{api,jobs,domain/{scan,mods,profiles,configs,customizations,builds,deploy,hostpanel,assistant},fs-safe,db,secrets}`,
`src/web`, `src/shared/schemas`, `src/agent` (the deploy agent), `tests/{fixtures-gen,unit,golden,e2e}`; runtime data in `data/`.
Python was considered (best config libraries) but needs a JS front end anyway, i.e. two languages; Node/TS kept by decision.

## 11. Embedded Claude assistant

- Own manual tool loop in the backend on the Messages API, SSE to the browser (Tool Runner pauses poorly on UI approvals; the Agent
  SDK's Bash/Write surface is too wide to sandbox; the MCP connector needs a remote URL).
- ~12 small paginated tools: `list_tree`, `read_file`, `search`, `list_mods`, `get_mod`, `diff_mods`, `get_config`, `merge_preview`,
  `read_log`, `read_memory`, `propose_patch`, `propose_memory_note`. **Read-only by construction**: proposals apply only after a UI
  click with a hash recheck.
- Models: `claude-sonnet-5-5` default; `claude-opus-5-5`, `claude-haiku-5-5`, `claude-fable-5-1` selectable. **Sonnet 5.5 defaults to
  effort `high`, so the app sends `medium` explicitly**; adaptive thinking only; forced `tool_choice` returns a 400 [verified by the
  research, not independently re-checked].
- **History is append-only** (thinking blocks are tied to earlier history): redact **before** appending, apply settings changes as
  appended messages, model/effort/tool changes apply to new conversations only.
- Safety: path sandbox (realpath, no junction escape, no UNC/ADS/device names), deny-list files at `read_file` level
  (`server.properties`, webhook configs) **plus** pattern redaction (patterns alone miss unknown secrets), third-party text wrapped
  as untrusted data, audit log with request-id and cost, per-tool allow/ask/deny, per-conversation and daily/monthly caps (hard stop).
- Settings UI: model, effort, max tokens, cache TTL, compaction, budgets, tool permissions, redaction rules, allowed roots, memory
  notes, system-prompt **append** (override behind an expert toggle). API key in the Windows Credential Manager, never sent to the browser.
- The researched system prompt is stored as `src/server/domain/assistant/system-prompt.md`. Skills as buttons: crash analysis,
  "why does this mod fail on the server", changelog + welcome drafting, explain a config key, blacklist suggestions, guided update.

## 12. UI

Dark, dense, one accent colour plus semantic status colours (added / removed / changed / conflict), icons + text, French copy,
keyboard-first (`j/k`, `a/r`, Ctrl+K, `?`). Two modes on the same views: the **update wizard** (section 7 order, resumable, "to
decide" counters) and free exploration. Pages: Dashboard, Update wizard, Profiles (the matrix), Mods, Configs (3-way + editor),
Harvest, Memory, Build, Test, Server (host panel), Watch (new BASE / mod releases), Assistant, History.

## 13. Security

Bind to localhost + LAN IP (firewall `LocalSubnet`), single password (scrypt/argon2), `HttpOnly` + `SameSite=Strict`, `Origin`/`Host`
checks, rate-limited login. `safePath` on every path; zip-slip and zip-bomb limits; writes only inside allowlisted roots, atomic, with
backup. Every outward action (deploy, publish, notification post) is dry-run first, needs an explicit click, is idempotent by id and
HMAC-authenticated. Outbound calls only to an allowlist (Anthropic, Modrinth, CurseForge if configured, update URL; the host panel is local to
the agent). CurseForge API terms forbid sharing the key and **caching API data** [verified]: only the derived decision and ids from
the user's own files are kept, and the CurseForge API stays optional.

## 14. Invariants the implementation must always guarantee (tests assert them)

1. Never write to a server or client instance while its process runs (check the process and `session.lock`).
2. Every apply/deploy is journaled; a crash resumes or rolls back, never half-applied.
3. Rollback = files + world, from a backup taken while the server was stopped.
4. No deploy while live drift against the baseline is unharvested or explicitly discarded; every write checks `expected_pre_hash`.
5. A server baseline is captured after every successful first boot, before any tweak.
6. Mods are compared by top-level mod id per jar; jar-in-jar is informational; a duplicate id blocks the build.
7. Only exact-path config matches with a matching guard apply without a click; a guard mismatch is a conflict.
8. Snapshots are immutable, content-addressed and reference-counted; retention never deletes the last healthy deploy.
9. Every outward action is dry-run first, needs an explicit click, is idempotent and authenticated.
10. Secrets never reach logs, UI, AI payloads or the DB in clear text; SMB sources are opened read-only; packs are built from clean trees only.

## 15. Roadmap (each phase ships something usable)

| Phase | Content |
|---|---|
| 0 | Skeleton: logon task, auth, DB + blob store, jobs/SSE, safe filesystem, fixtures generator, profile model |
| 1 | Import BASE-S / BASE-C / OWN-C, mod diff by mod id, loader check, blacklist from BASE sets, anomalies, decisions memory |
| 2 | Config engine (profiles, 3-way, integrated editor), customization memory + replay, **harvest** (minimal read-only agent snapshot endpoint + SMB read), secrets masking |
| 3 | Player/server pack builds, welcome message + changelog, boot test, `launched` capture |
| 4 | Full deploy agent (journal, host panel, world backup, rollback, baseline), CurseForge publish (dry-run + click), notification webhook, watch |
| 5 | Claude assistant (read-only tools, then approved proposals), budgets, skills |
| Later | other loaders / MC versions (key mapping), `.mrpack`, multi-profile, world restore UI |

Phase 1+2 are the MVP (the recurring pain: mods and configs).

## 17. Open questions (decision-changing; defaults above apply meanwhile)

1. **BASE client source**: an untouched BASE client instance on the Studio PC (jars on disk), or only the CurseForge client ZIP
   (ids only, needs a CurseForge API key)?
2. OWN **public** on CurseForge (needs BASE derivative permission) or unlisted/private? The CurseForge project and an author token are needed either way.
3. Does OWN add mods **not on CurseForge**?
4. Monthly AI budget, hard stop or warning?
5. Any access beyond the LAN, ever?

## 18. Risks

CurseForge third-party restrictions and API terms; side detection stays heuristic (hence boot test + remembered decisions); config
format variety (hence the line-patch fallback); the host panel API contract must be read on the server PC; scope creep (hence the phases);
a world corrupted by a mod change (hence the mandatory world backup); BASE licence for derivative public packs.
